# Real-user reliability audit and repair

2026-10-09, Asia/Tashkent. Local investigation based on deployed application `f44a7f7` and documentation `1a46b62`. Production was not contacted or changed for this task. No deployment, GitHub push, production migration, or production student write occurred. Local commits and isolated fixtures are the verification boundary.

## Why earlier green tests missed these failures

1. Default Playwright starts Vite with a fixture API URL; many suites replace RPC/REST responses with `page.route`. These test interactions, but cannot establish PostgREST signatures, row limits, RLS, or actual transaction acknowledgements.
2. Native suites skip unless PostgreSQL/PostgREST paths are configured. Default unit success can therefore omit transport and multi-connection tests. `npm run test:reliability` now checks tool availability and versions and fails if missing, rather than silently skipping.
3. Previous native journeys had one student and one admin with 32 questions. They did not exercise 500-item request sizes, a 5,000+ recurring pool, concurrent student accounts, or a full browser-process restart.
4. Native PostgREST previously lacked the managed service's usual 1,000-row cap. With that cap enabled, a realistic 1,001-attempt fixture proved silent truncation. The helper now explicitly sets `db-max-rows=1000`.
5. Version-adapting legacy SQL fixtures and optimistic UI assertions can conceal compatibility/persistence errors. New tests send real stale and versionless requests, inspect HTTP acknowledgements and revisions, and independently query stored rows.
6. The earlier PostgreSQL16/PostgREST16 path missed PostgREST14 serialization retry behavior. Native verification here requires PostgreSQL17/PostgREST14.
7. Fresh accounts alone miss history-dependent query costs. A representative older-account fixture now has 2,000 historical sessions, 6,000 items, and 531 eligible questions.
8. Fixture Auth/Storage do not reproduce managed provider revocation, signing, CDN caching, or deployment settings. A passing local journey remains local verification.

## Suspicions not reproduced

The Book checked-progress predicate initially looked MCQ-only. The actual native browser regression `tests/book-open-progress.test.js` passed without changing it: an un-checked typed selection counts zero, an incorrect Check counts one checked/zero solved, and correction counts one checked/one solved. `check_book_practice_response` in migration `20261005000500_vocabook_package_and_book_checks.sql` stores `selected_answer=0` as the compatibility marker. This was a coverage gap, not a newly confirmed bug. The regression is retained; no unnecessary query change was made. Similarly, the dashboard typed-response predicate is compatibility hardening for historical fixture rows without that marker, not proof that the existing automatic grading workflow drops typed answers.

## Remaining risks and known limitations

- No hosted verification or release of these local changes. Pending migrations need separate review and deployment approval.
- Managed Auth refresh/revocation, managed Storage signed-URL expiry, real mobile OS background eviction, many-hour sessions, browser storage deletion/quota, and broad production-account history are not fully verified. Expired JWT rejection and refresh recovery use a local Auth fixture.
- Study-time RPC credit uses elapsed wall time since the previous heartbeat and has no idempotency token. Multiple positive per-position requests in one batch may be undercredited, and ambiguous lost acknowledgements cannot be repaired by blindly replaying time. The frontend batching fixes do not establish exact per-question time accounting. Answers use a separate revision/idempotency contract.
- Existing audit C13 remains: the isolated book-reset operator test aborts with `Protected data changed: question_bank_eligibility`. No content-reset operation was executed on production; the protective guard must not be removed to make this green.
- Audit C15 and C16 are now reproduced/repaired as R09/R10 above. Source-package pixel tests remain dependent on unavailable original package fixtures.
- Provider security settings, very large group administration, and single-set Vocabulary limits from the old audit are not established as repaired by this suite.

## Release boundary

Frontend repairs need deployment approval. Apply `20261009000300_daily_homework_indexed_pool.sql` before exercising new broad recurring saves; existing JSON versions remain readable. `20261009000400_book_progress_history.sql` keeps the existing RPC contract. `20261009000500_admin_homework_overview.sql` adds the scoped admin counts without changing authorization or stored records. These are new pending migrations, not a reason to reapply the four already released October8 migrations. New daily versions still freeze all eligible snapshots, so their storage/write cost grows with the pool; daily start fetches only chosen snapshots and the browser never downloads the full pool.
