## Answer persistence and concurrency

`practice-persistence.js` writes pending answer fields to local storage synchronously before issuing a request. Records contain the owner/session-scoped item ID, expected revision, answer/response, mark/elimination and recovery metadata; they contain no source question or grading key. An acknowledgement must explicitly include every submitted item and its revision. Missing acknowledgements, connection failures and conflicts remain visibly unsaved. The UI displays “All changes saved” only after acknowledgement or after loading authoritative data with no pending edits.

Only dirty items are saved. Requests are serialized per player, and an earlier acknowledgement cannot clear a later local edit. Server updates use per-item `answer_revision` compare-and-set under the session lock. Different questions can commit independently. Conflicting writers to the same question receive SQLSTATE `40001`; an atomic batch conflict rolls back the entire batch. An identical retry is accepted when the first save committed but its acknowledgement was lost. Partial field payloads inherit authoritative omitted fields instead of clearing answers.

On navigation/reload, compatible pending answers recover automatically and retry. Conflicting drafts display saved and pending values and require an explicit decision. Removed questions and submitted sessions cannot receive recovered writes. Private persistence helpers and versionless legacy saves cannot bypass authorization/concurrency protection. Check RPCs preserve their existing event idempotency while rejecting a choice/response different from an already acknowledged answer. Check reloads authoritative versions afterward.

Browser storage failure is visible, and sidebar navigation plus ordinary refresh/close are guarded while answers remain unsaved. There is no guarantee for an **unacknowledged** answer if the browser cannot store the recovery draft and is forcibly closed, or if storage failure coincides with an offline browser-history SPA exit. This limitation does not affect successfully acknowledged database answers. Clearing browser storage deliberately also deletes unsaved drafts. No background retry while the player is closed is implemented; reopening the session or Retry saving retries compatible drafts.

## Assignment authorization and snapshot policy

One-time recipient additions create/reactivate the unique assignment and synchronize unfinished attempts. Group and active/all-student roster changes use the same synchronization. Removal soft-withdraws the assignment, rejects unfinished session reads/writes at the database, and keeps progress available to administrators. Rejoining students recover a synchronized unfinished attempt. Completed removed assignments retain legitimate read-only history.

For one-time edits, not-started students open the current definition. Started unfinished attempts receive the current definition; an unchanged source question **and frozen key** retains its item ID, saved answer, mark and elimination. Removed/replaced/re-keyed items and their keys are archived privately before removal, preserving historical answers. New items start unanswered. Completed attempts keep their original immutable snapshot. Unsaved drafts for removed items are retained locally for explicit review, never silently moved to another question. Existing in-flight saves either commit before archival or receive a conflict/access error. Definition and recipient changes are atomic.

Recurring versions, roster changes and template edits apply from the next local day, preserving today's started and previous completed occurrences. Dates and deadlines use Asia/Tashkent. Unfinished non-late instances reject reads/writes after their due time; completed history remains readable. Existing daily suites cover start/deadline boundaries, pause/resume, version changes, missed days, direct/group recipients and unique instances; the SQL-backed browser completes one occurrence and verifies administrator status. The audit's separate premature question-reuse bug C11 remains unresolved.

## Reproduce

Use Node 22.12+ or 24+, installed project dependencies and Playwright Chromium. Database/browser suites should run sequentially on this low-memory machine.

```sh
npm test
npm run test:e2e -- --workers=1
npm run lint
npm run build
node --test --test-concurrency=1 tests/practice-persistence.test.js tests/practice-answer-integrity.test.js tests/homework-lifecycle.test.js tests/homework-completed-history.test.js tests/practice-attempts.test.js tests/book-package.test.js
SATCHI_TEST_POSTGRES_BIN=/path/to/postgres/bin node --test tests/postgres-concurrency.test.js
git diff --check
```
